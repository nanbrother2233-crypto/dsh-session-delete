# dsh-session-delete

列出 DSH 已知的**全部工作区**会话，并彻底删除。

DSH 自带的「归档会话」只是把会话隐藏起来、数据仍然保留。本插件是它的破坏性对位物：
删除会话日志、投影缓存检查点以及引用它的索引；对仍在运行、或无法无歧义解析的会话一律拒绝。

## 它提供了什么

右侧面板新增 **Sessions（会话管理）** 标签页，出现在该面板的「添加标签页」菜单里，与内置的
Files 标签页并列。它显示：

- 跨全部工作区的会话，按时间从新到旧、按工作目录分组，且显示的名称与内置会话列表完全一致
  （依次取日志标题、工作目录名、id）；唯一例外是子代理会话——它直接显示自己被派去做的那件事
  （`subagent/descriptor` 的 `label`，例如 `Research DSH session storage`），而不是折叠出来的
  首条提示词标题，否则同一批里执行不同任务的几个子代理会读起来一模一样；
- 对标题、父会话、工作区路径与 id 的搜索；
- 子代理会话**缩进显示在它所属的父会话下面**，一次选中会连带删除哪些会话一眼可见；每一行子会话
  还同时带着 `↳ 父会话名` 标识——缩进只说明它排在哪里，父会话滚出视野或被搜索过滤掉之后就说
  不明它是谁的子代理了（内置侧栏完全不列出子代理会话，这里是唯一能看到它们的地方）；
- 运行中的点标记，以及删除该会话会一并带走的子会话数 `+n`（悬停可见文字说明）；
- 多选，以及一个确认弹窗，明确说明将要删除多少个会话、其中多少个是子会话。

弹窗会提示内置的「归档会话」作为非破坏性替代方案——因为这里的「删除」就是字面意思。

## 删除会移除什么

| 目标 | 说明 |
| --- | --- |
| 会话日志目录 | `<数据目录>/sessions/<项目>/<id>/` 整个目录：当前代与全部旧代（`session.jsonl.zstd`、`session.vN.jsonl.zstd`，以及锁附属文件）。 |
| 投影缓存 | `session_projcache` 中该会话的记录。宿主提供 storage-domain 表时走该表删除，以保持内存中表的一致性；否则直接删除磁盘文件。 |
| 历史缓存 | 第三方会话插件写入 `dsh-session-plugin-history-cache.json` 时，移除其中该会话的条目。 |
| 工作区归属 | 注册表提供 detach 能力时，把该会话从所有列出它的工作区中摘除。 |

正在使用的数据目录会打印在弹窗页脚，因而始终能看清当前操作的是哪个 `$DSH_HOME`。

## 它会拒绝什么

只要有一行被阻止，**整个计划**都会被阻止：什么都删不掉，包括那些本身没有被阻止的行。

| 拒绝原因 | 理由 |
| --- | --- |
| **正在运行** | 插件无法关闭活跃会话——detach 的 disposer 属于创建它的 fiber；而且活跃写入者会直接重建被删掉的日志。拒绝是唯一诚实的回答。请先结束该会话。 |
| **当前打开** | 承载本标签页的那个会话会随每次请求一起发送并被拒绝，包括它只是所选会话的**后代**、并未被直接勾选的情况。 |
| **磁盘上 id 重复** | 两个项目目录声称拥有同一个 id。后端在 `findLog` 中本身就拒绝解析这种歧义，这里若靠猜就可能删错会话。 |
| **从未落盘** | 创建了但从未写入的会话没有文件可删，而删文件并不能让它消失。 |

## 安全模型

harness 的 webserver 在分发前不做鉴权、也不做来源检查：**精确**路由会被直接匹配并调用，
排在守护 DSH 自身 RPC 通道与 SPA 回退的 Connection 围栏之前。这三条都是精确路由，而其中一条
会销毁用户数据。因此：

- 所有变更类路由都要求 `content-type: application/json` **以及**
  `x-dsh-session-delete: 1` 头。二者都属于非简单请求，浏览器必须先预检：跨站表单提交或
  `no-cors` fetch 根本到不了处理函数；
- 删除还额外要求请求体带 `confirm: true`，因而被截断或重放的请求本身删不掉任何东西；
- 计划在执行时重新构建——因为预览与确认是两次独立往返，期间会话可能转为活跃；
- 会话日志通过「目录名恰好等于会话 id 的**单射**编码」扫描定位。id 从不直接参与拼接路径，
  且该编码不可能产出路径分隔符，因此恶意 id 无法逃出所属项目目录。

这只是抬高了门槛，不是沙箱。任何能访问本机端口、并能自行设置请求头的程序都能访问这些路由。
对该端口裸发请求仍可能收到 `401 unauthorized`——那是 DSH 加在**它自己**路由上的围栏，
并不挡在这些路由前面。

## 安装

```
dsh plugin add --save-exact dsh-session-delete@0.1.0
```

然后重启 DSH Desktop——桌面端只在启动时激活新的 bundle。

发布出来的 tarball **就是插件本体**：22 个文件、压缩后约 51 kB。安装时没有任何构建步骤，也不
自带依赖树——宿主半边是编译好的，运行时只 import Node 内置模块与 `@deepseek-ai/dsh-home-paths`；
浏览器半边是预打包产物，除了 shell 注入的三个平台模块外什么都不 require。因此同一个包可以装到
任何跑得动 DSH Desktop 的机器上，完全不需要插件的开发目录：

```
npm pack                                        # 得到 dsh-session-delete-0.1.0.tgz，约 51 kB
dsh plugin add --save-exact .\dsh-session-delete-0.1.0.tgz   # 或这个文件的任意一份拷贝
```

如果改成从源码目录安装（`dsh plugin add --save-exact link:D:\path\to\checkout`），会把整个工作
树链接进 profile，连开发目录一起——那是改插件时图方便，不是使用它的必要条件。

精确的稳定版本号不是建议：市场的安装路径会从 npm 解析 `dsh-session-delete@latest`，并要求
`version` 是精确的稳定版本、且 `dsh.bundle.patch` 有效，本包两者都已声明。发布到 npm 本身
并不会让插件出现在内置社区市场里——那需要一个 catalog provider 收录它——但上面的命令始终可用。

## 环境要求

- DSH Desktop 2.0.13 / `@deepseek-ai/dsh` 0.1.5-rc.2 —— 本插件的构建与验证所依据的 API 面。
- Node `^22.19.0 || >=24.0.0`。

## 已知限制

- **无法在内置会话列表里加行内删除项。** 那张行菜单硬编码在 `dsh-client-ui-workspace` 中，
  没有对外开放的 action 插槽，任何插件都加不进去。因此管理界面做成右侧面板标签页。
- **无法强制结束活跃会话。** 见上面的拒绝表。
- **子会话随父会话一起删除。** 选中一个会话会连带它的子会话，且先删子后删父，因而部分失败时
  不会留下父会话已消失的孤儿。
- **不是安全擦除。** 文件只是被 unlink，文件系统恢复工具仍可能找回字节。若有此需求请使用全盘加密。
